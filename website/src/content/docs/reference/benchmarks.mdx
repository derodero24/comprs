## Takeaways

From the run below, on x86-64 Linux with Node.js 24:

- **zstd is faster than gzip and brotli** in comprs, for compression and decompression alike, with a better ratio than gzip. LZ4 is faster still on most inputs, at a lower ratio. Against the zstd of `node:zlib` at the same level, comprs compresses 1.1–2.7 times and decompresses 1.4–3.6 times as fast, to the same size.
- **gzip decompression** is 3.5–16 times as fast as pako and 1.0–2.0 times as fast as `node:zlib`; fflate is faster on incompressible data and on 150 bytes. **deflate (zlib) decompression** is 1.5–5 times as fast as pako, and 0.8–1.3 times as fast as `node:zlib`.
- **gzip and deflate compression** of 84 KB of JSON is 1.5 times as fast as `node:zlib` and 4.2–4.7 times as fast as pako, at the same ratio within 1%. comprs compresses with zlib-rs, which follows the algorithms of zlib-ng: on extremely repetitive input, such as one sentence repeated, it trades ratio for speed (82:1 against 122:1 for zlib), so the speeds on those inputs are not like for like. For 150 bytes, `node:zlib` is faster.
- **brotli** comes from libbrotli, the C library of `node:zlib`: it compresses to the same size at the same speed or faster, and decompresses up to 1.5 times as fast.
- **Node.js streams** of comprs are 3.7–7.9 times as fast as those of `node:zlib` for 1 MB in 16 KB chunks.
- These numbers are from the native addon; the WebAssembly build was not measured.

## How they are measured

The Bench Report workflow runs `scripts/bench-report.mjs` on a GitHub-hosted runner, with every library at the same settings, and writes the tables and the charts from that one run, with the versions, the machine and the settings above the tables. Run the benchmarks yourself with `pnpm run bench` in a clone of the repository; numbers vary by machine and data. [CodSpeed](https://codspeed.io/derodero24/comprs) tracks the Rust benchmarks on the pull requests that change Rust code, to catch performance regressions.
